# External corpus intake for a larger benchmark

This adds public source data beyond the eight authored v1 cases. **It does not add measured model results or claim that the imported tasks already work with this agent.** The v1 source, frozen plan and reported outcomes remain unchanged.

| Source | Imported unit and exact count | Useful scope | Current status |
|---|---|---|---|
| [KALM](https://github.com/dynatrace-oss/Kalm-Benchmark) | 241 manifest files: 238 labeled candidates and three support files; 445 resource documents | Static Kubernetes security patterns across 79 source rule families | Imported and checked; zero runtime-validated repair tasks |
| [ITBench-Lite CISO on Hugging Face](https://huggingface.co/datasets/ibm-research/ITBench-Lite) | 10 policy scenarios; 301 original YAML files and 10 reference Rego policies | Static security and compliance assessment | Imported and checked; not behavior-preserving repair ground truth |
| [Infra-Bench](https://github.com/kubeply/infra-bench) | 71 Kubernetes task definitions with 801 upstream assets | Runtime task instructions, environments, reference solutions and executable tests | Definitions imported; zero locally validated or agent-ready tasks |

These counts use different units. They must not be added and presented as hundreds of independent, executable security-repair cases. All three sources declare Apache-2.0; license text, original paths and pinned revision metadata are retained in their respective directories.

Original source bytes are checked against upstream Git blob hashes and recorded SHA-256 hashes. Importers do not run upstream scripts, deploy manifests or call a model. Imported shell scripts are stored without executable permission. This is an intake boundary, not an execution sandbox or permission to run them.

Corpus tooling requires Python 3.11+ and the optional pinned parser in [requirements.txt](requirements.txt). Core v1 source is unchanged. After installing that dependency in an isolated environment, run from the project root:

```bash
python3 -B scripts/audit_external_corpus.py \
  --check-summary benchmark/corpus-v2/quality-summary.json
python3 -B -m unittest discover -s tests -p 'test_*corpus.py' -v
python3 -B scripts/freeze_benchmark_plan.py --check benchmark/plan-v1.json
```

[quality-summary.json](quality-summary.json) is generated by an offline audit of the imported files, source pins, derived inputs, task counts and grouping. [External corpus validation](../../.github/workflows/corpus-ci.yml) installs the pinned optional parser and runs these checks in CI. No cluster or model workload is started by that workflow.

## Model inputs and protected references

The complete corpus includes expected answers and verifier code. **Do not mount the corpus root into an evaluated agent's workspace.** Use [export_corpus_input.py](../../scripts/export_corpus_input.py) to create a fresh input-only workspace:

```bash
python3 -B scripts/export_corpus_input.py --source infra-bench \
  --candidate-id fix-restricted-security-context --output runs/input-only-example
```

Only the resulting `agent/` directory is intended for the model. The sibling receipt is operator provenance. An export creates input files only; it does not turn a task into a validated repair experiment.

KALM's answer annotations and descriptive benchmark identifiers are removed from its static agent views. Runtime-relevant annotations remain. ITBench views omit compliant targets and reference policies and remove explicit oracle metadata keys; public workload names can still hint at answers. Infra-Bench exports only task instructions. Packaging alone does not enforce filesystem isolation: a future runner must expose only the approved directory and tools.

## Duplicates, splits and source-quality findings

KALM contains 241 distinct raw files but only **232 identifier-normalized structural groups**. The importer keeps exact/structural duplicates and related source rule families together. The resulting assignment is **59 development, 179 evaluation candidates and three support files**. This does not establish independence, hidden evaluation or absence from model training data. The normalization does not detect every possible template relationship.

ITBench's dataset card advertises 15 CISO scenarios; the pinned files provide **10**. Five advertised scenarios are absent. Several README topic descriptions also disagree with the actual task text/reference policy, so task contents are used for interpretation. Its 301 YAML files include per-resource and aggregate representations; they are not 301 independent cases. Keep each entire policy scenario together in any future split.

Infra-Bench includes broad operations tasks, not just security. Its upstream `access-and-isolation` category contains **nine candidate tasks**, listed in the quality summary. Literal security keyword matching finds 31 tasks, but those are discovery hints, not validated security labels. The first container-hardening adaptations to inspect are:

- `fix-restricted-security-context`
- `repair-restricted-multi-container-pod`
- `harden-payments-stack-without-breaking-runtime`

Their upstream tests inspect real cluster rollout, configuration, resource identity and application behavior. Their setup still needs adaptation: privileged k3s containers, mutable image tags, dependencies and protected baseline state have not been accepted as this project's execution environment. RBAC and NetworkPolicy candidates additionally require appropriate permissions and an enforcing CNI. No upstream test or solution has been executed here.

## Other datasets considered

[The Stack Kubernetes YAML subset](https://huggingface.co/datasets/substratusai/the-stack-yaml-k8s) reports **276,520 manifest rows** with original repository/path/license metadata. It is useful for discovering diverse workloads. No full shards were downloaded: per-file licensing, removals/terms, duplicate repositories, missing repair labels and missing application contracts must be addressed first. Rows in a code corpus are not executable remediation tasks.

Kaggle was also searched through its public API. [Kubernetes Commands](https://www.kaggle.com/datasets/thedevastator/kubernetes-kubectl-command-dataset) is command/description data; [Kubernetes Dataset](https://www.kaggle.com/datasets/usmanjutt17/kubernetes-dataset) contains traffic CSV data. Neither supplies configuration-repair tasks. The [Autonomous DevSecOps dataset](https://www.kaggle.com/datasets/beatsprom/autonomous-devsecops-and-kubernetes-agent-suite) advertises 2,500 SFT examples. Two inspected rows ask for controller code and test initialization/telemetry attributes; those checks do not establish deployed Kubernetes repair correctness. That small inspection is not an assessment of all 2,500 rows, and the dataset was not adopted as primary evaluation ground truth.

## Promotion to an executed v2 benchmark

A candidate needs an adapted isolated environment, pinned images/dependencies, a reproducibly broken initial state, an oracle repair that passes, and security **and application-behavior** tests protected from the model. Unsupported or ambiguous cases stay visible in an exclusion ledger. Split by workload/repository and repair family before model evaluation; do not count superficial identifier changes as independent workloads.

The current agent only supports its original bounded cache-service edits. It cannot execute arbitrary imported Infra-Bench tasks unchanged. Register a new source/protocol version after adapters and tests are validated, measure pilot costs, and set a bounded campaign before starting model comparisons. The previous 96-trial report remains a result over eight unique cases; **this intake adds zero model results and zero validated runtime cases**.
