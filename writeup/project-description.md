## Harness architecture

The template starts one headless Pi process per task. The evaluator connects to `serve.py` over WebSocket and passes the task instruction and limits. Pi receives a general engineering prompt and calls the sponsored Claude Opus 5.5 endpoint. Its tool extension relays file operations, shell commands, and task MCP requests through `taskbridge.py` into the isolated task container. The harness returns its final message through the same WebSocket. The evaluator exports the deliverables and their hashes to the artifact manifest. ## Insight and failure analysis

All 29 manifest entries have status `ok`. Four received zero reward. The foundation-strategy and solar-witness-test-package entries exported no deliverable files. The foundation trace ended on a tool call. The last solar witness-test observation recorded an unauthenticated OpenProject request. The two data-hall MEP routing entries each exported the requested `solution.py` and still scored zero. Their final messages reported local IFC validation and documented assumptions about how to interpret parts of the design. Those cases call for two distinct checks before the harness signals completion. First verify that the files required by the prompt exist at the requested paths. Then open the outputs with the appropriate parser and validate the constraints the prompt makes testable. The individual failed routing grader checks remain unverified. ## Deliverable-first verification prototype

The archived outcomes motivated a separate candidate on the same Pi version and Claude Opus 5.5. Pi records the exact file paths requested by the task and drafts usable outputs early. It checks hard constraints and units before optimization, and can replay scripts or read back application state with task-local inputs and tools. This ordering matters on design-objective tasks, where a missed hard constraint can remove the entire objective component of the score. [Organizer scoring rules](https://github.com/google-research/ple/blob/5cf736f8b6e6f28eea71cae52de0c3bedaa88fa2/docs/rules.md)

A read-only audit runs in the task container and checks declared files for existence, nonempty content, and basic format structure where supported. A structural failure or absent final answer can trigger one repair phase capped at four minutes. The harness audits the output again when time allows. Response-only and app-only tasks can complete without a file audit. The audit checks file structure. Engineering validity still depends on task-specific checks and official grading.

The local prototype passed **10 offline integration scenarios with simulated Pi replies**, covering missing and malformed files, a bounded repair, app-only completion, and cancellation. Its configuration passed static kit validation. The official comparison will pair current-set rewards using the same model, grader, and time budget, then disable repair in a third run to isolate its contribution. Report paired task rewards, zero-score counts, output coverage, repair outcomes, elapsed time, and available model cost. The candidate’s official score is pending.

## Cross-model generalizability

The organizers benchmarked the Pi harness with multiple models on the same 29 development tasks, averaging each pairing over three runs. Pi scored **0.563 with Gemini 4 Neon**, **0.502 with Gemini 4 Hydrogen**, **0.474 with Claude Opus 5.5**, and **0.270 with Gemini 3.8 Flash**. Relative performance varied by discipline. Hydrogen led Opus on civil tasks, 0.665 to 0.590, while Opus led Hydrogen on mechanical tasks, 0.393 to 0.361. These results describe the organizers’ benchmark cohort. A separate cross-model run of the prototype would hold the prompt, tool allowance, and grading fixed and report paired task outcomes. Its cross-model results are pending.
